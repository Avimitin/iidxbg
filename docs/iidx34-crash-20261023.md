# IIDX34 crash after changing song-select video source

Investigated 2026-10-24. User reported changing song select from a fixed local
video to Bilibili favourites during the last launch. The exception in `log.txt`
is timestamped **2026-10-23 23:54:15**, thread 2264.

## Confirmed failure mechanism

`log.txt:10384` reports `EXCEPTION_ACCESS_VIOLATION`, RIP
`bm2dx.dll+0x338F00`, instruction `jmp rax`, with
`RAX=0x3F8000003F800000`. Both 32-bit halves are the IEEE-754 representation of
`1.0f`; this is not an executable callback address. The reported access address
`0xFFFFFFFFFFFFFFFF` accompanies this noncanonical jump target and should not
be mistaken for a normal null-pointer read.

The native function at RVA `0x338900` takes six arguments under the Microsoft
x64 ABI. Its sixth argument is optional render user data. At `0x338EDD` it tests
`u32(user_data+4)==0x10000`, at `0x338EE6` it loads the post-draw callback from
`user_data+32`, and at `0x338F00` it tail-calls that callback. It does not validate
the user-data length before doing so.

The dump retains the sixth argument in the caller's stack slot at
`0x11AED78`: **`user_data=0xF72FD3C4`**. Its bytes are:

| Location | Value / meaning |
|---|---|
| `user_data-4` | `16`: actual payload length |
| `user_data+0` | `0` |
| `user_data+4` | `0x10000`: interpreted as custom shader marker |
| `user_data+8` | `0x115392010`: opaque pointer, target not captured |
| `user_data+32` | `0x3F8000003F800000`: outside the 16-byte payload |
| `user_data+40` | `0`: also outside the payload |

This is an **out-of-bounds callback read from a short AFP user-data block**.
It is not necessary to assume that the video texture descriptor was freed to
explain the fault.

The length prefix is verified from `afp-core.dll` ordinal 51, export
`XCd229cc000032` at RVA `0xBC20`, delegating to `0x7E80`: allocate `length+4`,
write the length, copy exactly `length` bytes, store as property type 16/key 55,
and set object flag `0x200000`. AFP render traversal at `0x5860` retrieves this
property and publishes the payload pointer (`allocation+4`) at `0x5906`.

AFP's primitive emitter `0x26C0` forwards that pointer to the packed command.
The dump has the same pointer at `0x55273A8` and `0x50F42F0`. The final command at
`0x50F42E0` is opcode 7, size 104, four vertices. Its parameters indicate an
untextured rectangle, with corners spanning **1920x1080**. It is emitted through
the native viewport/mask rectangle path (`afp-core+0x56D0`, caller `0x8A30`).
It is not a textured draw of the newly selected Bilibili video.

`afp-utils+0x1C080` dispatches the command to `bm2dx+0x34FED0`, which forwards
its fourth argument as the sixth argument to `0x338900`. The latter draws the
rectangle and then attempts the invalid post-draw callback. This matches the
recorded call stack through `bm2dx+0x34FF67`, AFP packed-buffer flush, and AFP
render traversal.

## Strongest explanation for the malformed block

There is a matching uninitialized-padding defect in native primitive data:

- `CBoxFillPrim` constructor `bm2dx+0x339820` writes DWORD `this+40` and QWORD
  `this+48`, leaving DWORD **`this+44` unwritten**.
- Its update at `0x339DB0` again writes only `this+40` and `this+48`, then calls
  AFP ordinal 51 with **16 bytes** starting at `this+40`.
- `CBoxPrim` (`0x3393B0`, update `0x3397F0`) and `CLinePrim` (`0x33B840`, update
  `0x33BB10`) have the same padding/copy pattern.
- Their payload is `{u32 count, uninitialized u32 padding, pointer}`. If the
  padding contains `0x10000`, the generic rectangle renderer mistakes it for
  the much larger custom-shader structure.
- The legitimate native sprite custom-shader setter at `0x336E70` supplies
  **48 bytes**, with callbacks at payload offsets 24 and 32 and context at 40.

The captured 16-byte payload matches the primitive format. The native padding
defect plus the renderer's unchecked interpretation explains the observed
marker and out-of-bounds callback. Allocation/scene timing changes could expose
this when switching sources. That timing relationship is an inference, not a
proven allocation history.

The exact originating C++ primitive instance is **not identified**: its pointer
target and owner are absent from the minidump. Therefore the dump does not prove
which primitive class supplied this instance, whether another plugin affected
its allocation, or whether a separate state/lifetime bug contributed. Do not
claim that a specific iidxbg texture destructor or the favourites API is the
proven root cause.

## Provider sequence and limits

The plugin log first shows successful local-video preparations, then a config
reload and successful cached Bilibili song-select preparation, followed by
`Custom selection AFP background artwork ready`. Another preparation of the
same Bilibili video completes before the final shutdown invalidation. The log
does not timestamp individual plugin events, so it cannot establish the exact
frame delay from changing the option to the exception.

The crash log reports about 10 GiB commit headroom. Neither an out-of-memory
condition nor a decoder exception is shown in this stack. Missing assistant
character image warnings precede the crash, but there is no demonstrated causal
connection between those warnings and this invalid callback.

## Reproduction and next verification

Reported sequence: run the exact recorded game/plugin builds, start with a
fixed local song-select video, change song select to Bilibili favourites, and
continue through gameplay/results back into song select. Existing captured
evidence includes those transitions, but this investigation did **not** rerun
the game or reproduce the crash independently.

Offline verification used PE-backed Capstone disassembly, IDA/Hex-Rays, and the
minidump memory-list stream. The private helper
`target/crash-20261023-235415/inspect_dump.py` prints the callback instructions,
retained stack addresses and relevant memory. To verify manually, inspect the
sixth argument above, read its preceding length DWORD, and compare payload+32
with the logged RAX. Decompile the listed constructors and updater functions
to check the missing padding writes and 16-byte copy.

The initial investigation changed no binaries or deployed settings. The
following mitigation was implemented separately in response to the request
for a workaround.

## Workaround: initialize primitive padding before publication

The plugin hooks the three native primitive update functions listed above,
only for game hash `c98e183e...6534` (full hash in Inputs). Each new entry has
a 16-byte file/live-code guard in `src/profiles/iidx34/010-20260917.rs`. The existing validated
MinHook chaining policy applies. Other build profiles do not install them.

All three functions have the Microsoft x64 ABI `update(this)` with `this` in
RCX. The plugin forwards the original pointer exactly once and preserves RAX
on return. The native zero-handle path leaves RAX unspecified, so callers must
not interpret that value. For a nonzero DWORD handle at `this+8`, the hook
initializes DWORD `this+44` to zero **before** calling the original update.
Every other object byte remains unchanged by the hook. For a zero handle the
hook only forwards the call, matching the native no-publication path.

Lifetime evidence: these are instance update methods with live, writable
objects of at least 56 bytes. The original functions write count/pointer to
`this+40`/`this+48`, then tail-call AFP ordinal 51, which copies all 16 bytes
synchronously into AFP-owned storage. The hook retains no pointer, allocates
nothing, and performs no IO, decoding, or graphics operation. It runs on the
original caller thread, including when background replacement is disabled.
Both box updates are referenced by their class vtables at slot 4. The line
update is also called directly at RVAs `0x83320D` and `0x83842C`; the entry
detour covers those callers as well.

This producer-side workaround avoids reading an assumed AFP length prefix
from arbitrary render inputs, replacing buffers during drawing, or disabling
legitimate shaders. The sprite shader setter at `0x336E70` and native renderer
remain unchanged. No game DLL or game asset on disk is modified.

### Offline verification

Run `py scripts/verify-primitive-padding.py <path-to-exact-bm2dx.dll>` with
`pefile` and `unicorn` installed. The script validates the input hash and new
entry guards, then emulates the **actual native updater instructions** with a
mocked AFP ordinal 51. For all three classes, count 0/4 and active/inactive
handles, it verifies publication size/count/pointer and return forwarding.
Seed `this+44=0x10000`: without initialization the original post-draw branch
attempts the dump's invalid `0x3F8000003F800000` callback; with initialization
the same instructions skip that callback. A separate genuine 48-byte shader
control still reaches its callback. The callback test begins at `0x338ED8`
and stops before the indirect jump at `0x338F00`; it does not emulate Direct3D
or run the complete game.

Rust regression tests check that the hook changes only the padding DWORD,
calls the original once, preserves its return value, leaves inactive objects
untouched, and has entry guards only for the analyzed build. The core suite
passes: 49 passed, 3 environment-dependent tests ignored. Clippy with warnings
denied, formatting, release build, all 42 static runtime guards, and the DLL
load/export/SDK-ABI smoke check pass. The workaround release DLL SHA-256 is
`e55bdfe2408118f5931f097b66f0f12b676ce27d5543bf00c9546f14a11ff761`.

### Remaining validation and limitations

The original primitive instance is still unknown. This fixes the verified
uninitialized-padding defect and prevents its matching failure mechanism; it
does not establish that every possible source of malformed AFP data is fixed.
An already-published corrupt payload is not retroactively repaired. Start a
fresh game process with the rebuilt plugin before testing.

**Actual in-game testing has not been performed for this workaround.** Repeat
the reported local-video to favourites switch, play/retire through results,
and return to selection several times; check both displays and shader effects.
Keep the original dump for comparison if another exception occurs. Deployment
and this reproduction remain pending.
